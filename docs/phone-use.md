# 屏幕读取与应用控制（YIIAI 的眼睛和手）

YIIAI通过一个**无障碍服务**看到你的屏幕、帮你点击和输入。没有用录屏授权，所以截图时不弹授权框、也没有录屏提示条。

**视觉优先，控件树辅助**：模型主要靠持续的屏幕画面理解你在看什么；控件树只用来精确定位按钮坐标。原因很直接——控件树只有结构和文字，用户看到的图片、视频帧、商品图、弹窗样式它都读不到。

## 开启方式

系统设置 → 无障碍 → 已下载的应用 → **YIIAI** → 打开。

App 内的引导：设置 → **屏幕与应用控制**，页面顶部会显示当前状态（未开启 / 已勾选等待连接 / 已开启）。

> **HyperOS 会在重启、强杀进程后自动关闭无障碍服务**，这是系统保护机制，不是 App 的问题。
> 处理方式：
> - 服务第一次成功连上后，App 记下「曾经开通过」；
> - 之后回到 App 时如果发现它又被关掉，首页顶部会出现一条红色提示，点一下直接跳到开启页面；
> - 设置里「屏幕与应用控制」那一行用胶囊滑块显示当前状态（开 / 关）。

## 模型能调用哪些工具

工具在 `app/src/main/java/com/yiiai/app/live/Tools.kt` 里定义，随 `session.update` 一起下发。协议要求每个会话的这份列表逐字一致，所以描述和参数都不含动态内容。

| 工具 | 作用 | 只读 |
| --- | --- | --- |
| `look_at_screen` | 看一眼并**开启持续画面流**约 180 秒（tagged-v1 的 0x02 帧） | 是 |
| `watch_screen(seconds?)` | 持续观看屏幕 30–600 秒（默认 180），或给正在进行的观看续期 | 是 |
| `stop_watching(target?)` | 停止看屏幕 / 关摄像头（`screen`、`camera`、`all`，默认 `all`） | 否 |
| `look_at_camera(facing?, seconds?)` | 视觉开关开启时打开前/后摄，连续发送 3–120 秒画面后自动关闭（0x01 帧）；已开着时是续期 | 是 |
| `read_screen` | 读取当前界面的文字与可点击元素，带序号和坐标 | 是 |
| `tap_screen(x,y)` | 按坐标点击 | 否 |
| `tap_element(index\|text)` | 按序号或文字点击 | 否 |
| `swipe_screen(x1,y1,x2,y2)` | 滑动 / 滚动 | 否 |
| `press_key(back\|home\|recents\|notifications)` | 系统按键 | 否 |
| `type_text(text,index?)` | 往输入框里输入文字 | 否 |
| `list_apps(query?)` | 查设备上装了哪些应用，可按关键词过滤 | 是 |
| `open_app(app)` | 按应用名或包名打开 App，找不到时返回相近名称 | 否 |

调用流程按协议走：`response.function_call_arguments.done` → 本地执行 → `conversation.item.create`（function_call_output）→ 收到 `conversation.item.created` → `response.create`。
如果服务端没有回 `item.created`，客户端 1.5 秒后自己发 `response.create`，避免这一轮卡住。

## 摄像头视觉

- 设置 → **开启视觉**。首次开启时申请 Android 相机权限；默认关闭，关闭后模型工具会拒绝摄像头调用。
- 开启后可选默认前摄或后摄；用户明确要求自拍/看环境时，模型也可在工具参数中临时切换镜头。
- `look_at_camera` 由模型根据「你看一下」「快看」等语义调用。镜头打开后**连续发送一段时间**的画面再自动关闭：
  - 时长默认 **5 秒**；模型可用 `seconds` 指定 3–120 秒；
  - 帧率、长边、JPEG 质量由摄像头画质档位决定，标准档 10 秒约 10 帧；
  - 镜头开着时再次调用是**续期**，不会重新打开；`stop_watching` 或首页的「关闭」可以提前结束。
- 工具在**第一帧发出后就返回**，之后的画面在后台继续送，不会让这一轮对话一直等。
- 到时间、被其他应用抢占或出错时，会用 `session.thinking.append` 静默告诉模型「镜头已关闭」，并把主画面焦点还给屏幕。
- **首页预览**：镜头开着时，首页中间的小鹿换成镜头画面（前摄镜像），左上角显示镜头和倒计时，右上角可关闭，小鹿缩到左下角继续反映通话状态。预览只在首页可见时解码。
- 采集用 YUV，自行转 JPEG 并把像素转正（按传感器方向和手机朝向），不依赖 EXIF；图片只在内存中处理，不落盘。
- 通话前台服务仅在视觉开关开启且相机权限已授予时声明 camera 类型；关闭视觉时移除 camera 类型，并关掉正开着的镜头。
- 若所选镜头不存在、相机被其他应用占用或权限被系统撤销，工具会返回错误，不会悄悄切换到另一颗镜头。

实现见 [CameraStreamer.kt](<app/src/main/java/com/yiiai/app/phone/CameraStreamer.kt>)。

## 屏幕画面流

- 帧率由屏幕画质档位决定（每 2 秒 1 帧 / 每秒 1 帧 / 每秒 2 帧），并通过 `media.configure.video` 声明。
- **画面没有变化时不重复发送**，只每 5 秒补一帧。
- 只在**通话中**、且用户停在别的 App 时推流；YIIAI 自己在前台时不推，**倒计时也停住**（最多停 3 分钟）。

### 一次观看的完整流程

| 阶段 | 行为 |
| --- | --- |
| 开始 | `look_at_screen`（180 秒）或 `watch_screen(seconds)`（30–600 秒） |
| 续期 | 模型再次调用 `watch_screen`；用户在首页点「加 3 分钟」。只会延长，不会缩短 |
| 自动续期 | 模型在操作手机（点击、滑动、输入、打开应用、读界面）时至少再留 90 秒；用户刚说过话至少再留 45 秒。自动续期累计最多比明确要求的时间多 10 分钟 |
| 快到期 | 剩 20 秒时静默通知模型「还没做完就调用 watch_screen 续期」 |
| 到期 | 关闭画面，静默通知模型「你现在看不到屏幕了」，首页提示「看屏幕的时间到了」 |
| 提前结束 | 模型调用 `stop_watching`；用户在首页或悬浮面板点「停止」 |
| 中断 | 无障碍服务被系统关掉：立即通知模型和用户 |
| 断线重连 | 记住剩余时间，重连成功后接着看 |

「静默通知」用的是 `session.thinking.append`：模型不会因此开口，但之后不会再假装自己还能看到屏幕。

首页状态条下方、悬浮面板里都会显示「正在看屏幕 · 剩 m:ss」；悬浮小鹿角上亮一颗小灯（屏幕为绿色，摄像头为红色）。

实现见 [LiveSession.kt](<app/src/main/java/com/yiiai/app/live/LiveSession.kt>) 的「看屏幕」一节和 [ScreenStreamer.kt](<app/src/main/java/com/yiiai/app/phone/ScreenStreamer.kt>)。

### 为什么用无障碍截图，而不是录屏（MediaProjection）

MOSS-Live 的视频输入是**一帧一帧的 JPEG**，帧间隔最短 200 ms（每秒最多 5 帧），不接收 H.264 等视频流。
所以无论用哪种方式采集，模型看到的都是一串静态画面，采集方式只决定「每秒最多能给几帧」和「用户要付出什么」。

| | 无障碍截图（现用） | 录屏 MediaProjection |
| --- | --- | --- |
| 最高帧率 | 约每秒 3 帧（系统限制两次截图间隔 ≥333 ms） | 不限，受协议限制为每秒 5 帧 |
| 授权 | 开一次无障碍服务 | **每次开始都弹系统确认框**（Android 14+ 不能记住） |
| 能否由模型在后台发起 | 能 | 不能，必须从可见界面发起 |
| 状态栏提示 | 无 | 录屏期间常驻提示 |
| 受保护页面（支付、部分视频） | 截不到 | 同样是黑屏 |
| 其他应用的声音 | 拿不到 | 可以申请采集，但很多视频应用禁止 |
| 点击、输入 | 本来就靠无障碍 | 仍然需要无障碍 |

结论：在现在每秒 1–2 帧的用法下，无障碍截图是更合适的默认方案——模型能随时自己开始看，不打断用户。
录屏只在需要每秒 3–5 帧或需要应用声音时才有优势，代价是每次都要用户点确认。
以上是按系统与协议规格做的对比，没有做过两种方式的实测对照。

## 画质与音质

设置 → **画质与音质**，角色声音提供标准和清晰两档；屏幕、摄像头画质分别选择。定义在 [Quality.kt](<app/src/main/java/com/yiiai/app/settings/Quality.kt>)。

| | 省流 | 标准（默认） | 清晰 |
| --- | --- | --- | --- |
| 音频（角色的声音，下行 PCM） | 不提供此档 | 16 kHz · 约 32 KB/秒 | 24 kHz · 约 48 KB/秒 |
| 屏幕 | 长边 720 · 质量 60 · 每秒 1 帧 | 长边 1080 · 质量 70 · 每秒 3 帧 | 长边 1280 · 质量 85 · 每秒 3 帧 |
| 摄像头 | 长边 720 · 质量 60 · 每秒 3 帧 | 长边 1080 · 质量 70 · 每秒 5 帧 | 长边 1280 · 质量 85 · 每秒 5 帧 |

- 麦克风上行固定 16 kHz PCM，不随档位变化。
- `media.configure.video` 只有一份，屏幕和摄像头共用：声明时取两路的最大长边、最高质量、最短间隔，两路再各自按档位采集。
- 画面档位通话中修改立即生效；音质档位下次接通时生效。
## 截图

- 用 `AccessibilityService.takeScreenshot()`（Android 11+），长边和 JPEG 质量按屏幕画质档位。
- 系统规定两次截图至少间隔约 333 ms；画面流和工具的截图在 `PhoneUseService.screenshot()` 里排队并补足间隔。
- 格式通过 `media.configure.video` 提前声明；服务端默认 profile 只有长边 512 / 质量 0.75，文字会糊。
- **`jpeg_quality` 必须在 0.1–1 之间**（传 80 会让整条 `media.configure` 被服务端拒绝，音频配置也会一起失效）。
- 发帧前先发 `video.state{source:"screen",enabled:true}`。
- 截图只在内存里转成 JPEG 直接走 WebSocket，**不落盘**。

## 应用列表可见性

Android 11+ 默认看不到别的应用，这是「打开淘宝却找不到应用」的根因。现在两道都做了：

1. `<queries>` 声明 MAIN/LAUNCHER intent 过滤；
2. **`QUERY_ALL_PACKAGES` 权限**（应用可见性总开关）。

枚举方式也换了：不再只靠 `queryIntentActivities`，而是
`getInstalledPackages()` 全量遍历 + `getLaunchIntentForPackage()` 解析启动入口。
这样被用户冻结、隐藏、或没有 launcher intent 的应用也能查到。
结果缓存 5 分钟（`AppCatalog`）。

实测：可启动应用 89 个，覆盖全部 88 个 launcher 包与 82 个第三方包。

### 按名字启动的匹配规则

精确包名 → 精确名称 → 去空格同名 → 名称包含关键词（关键词至少 2 个字，取最短命中）。

**不能**做「关键词包含名称」的反向匹配：应用名里有单字母的（如「X」），
任何带该字母的输入都会被它抢走，结果打开一个完全不相干的应用。

找不到时会返回设备上可启动应用的数量和前 20 个名字，便于模型直接点名重试。

## 首次启动

第一次打开 App 会先走一遍权限引导页（[PermissionSetupScreen.kt](<app/src/main/java/com/yiiai/app/ui/PermissionSetupScreen.kt>)）：
麦克风、通知当场申请；悬浮窗、无障碍说明后带路到系统页面，回到 App 自动刷新状态。
走完写入 `onboardingDone`，之后不再出现。

## 已知限制

- **截图失败**：支付、银行、部分视频 App 禁止截屏，`takeScreenshot` 返回失败，工具会如实告诉模型「当前页面不允许截屏」。
- **听不到别的声音**：无障碍只能看图，拿不到其他 App 的音频。
- **坐标是屏幕像素**：和截图分辨率一致，不随界面缩放变化。
- **复杂界面会点错**：准确度取决于模型对控件树的理解，必要时让它先 `read_screen`。
- **耗时**：截图 + 上传约 0.3–1 秒，模型会先说一句「我看一下」再回答。
- **未在真机验证**（2026-11-13 改动）：看屏幕的续期与到期通知、摄像头连续画面与首页预览、画质档位，目前只通过了编译。

## 安全

- 支付、发送消息、删除这类动作目前**没有**单独的确认弹窗；只有工具结果会进对话日志。
- 后续要做的是：把 `read_only:false` 且涉及金额/发送的动作改成先问用户确认再执行。
